# Agent entry point: create a useful project frame and build through it

Use this alongside the user's idea and target directory. Respect that project's existing instructions and authorization. Do the work already authorized; do not stop at a plan or ask again for routine reversible implementation. For a tiny task, use the existing project directly instead of forcing a new frame.

1. Read the intended outcome, genuine inputs and existing artifacts. Identify the first observable useful flow. Preserve an existing project authority; use `state_entry` to point at it instead of creating a competing plan. Classify useful existing assets as reuse/adapt/reference and check actual compatibility.
2. Map the complete intended capability set shallowly. Deepen only the first ready responsibilities. Split along coherent behavior and independently owned artifacts, with explicit inputs, outputs and observation-based acceptance. Stop before local decisions require constant cross-module negotiation; combine tightly coupled pieces. Unresolved architecture belongs in a bounded investigation before dependent construction.
3. Write `project.json` using the field contract in `docs/FOUNDATION-CONTRACT.md`. Give each module a native `home`, disjoint `owns`, purpose, responsible role, promised behavior and completion observations. Use `depends_on` for semantic consumers and `build_after` only for true dispatch prerequisites. Optional `parent` is a valid module ID. Name paths and interface schemas concretely. Do not put credentials in the brief.
4. Supply actual native artifacts using literal `content` or inspected `copy_from` files. Build a navigable whole: entrypoint, real signatures/schemas, module homes and first working connection where feasible. Explicitly mark unfinished stubs; they are scaffolding, not delivered behavior. No fake data or pretend success. For writing/research, native chapter/section/source files replace software interfaces; this domain transfer is a design option, not yet validated by the software example.
5. Run `python fluid.py validate BRIEF`, preview `frame BRIEF TARGET`, then `frame BRIEF TARGET --apply` within the user's authorized scope. Resolve actual collisions without deleting existing work. A differing evolved project is not an invitation to overwrite it. The tool does not run commands or launch workers for you.
6. Dispatch only ready work to the available native agents. Each reads the whole capability map, its scoped `context`, relevant real sources and neighboring contracts; claims its responsibility; implements within ownership; and records actual command/output observations. Use available workers in parallel only where boundaries allow it. Agents may review their own work, but a distinct reviewer should decide acceptance.
7. Connect useful parts as they become ready. Checks should answer a real question about the intended flow, interface, regression or uncertain claim. Preserve required project checks. Don't use test counts as completion or postpone a consequential integration risk until the whole product is built. Before repairing a failed check, compare its expectation with the actual source and user requirement: the evaluator can be wrong. Preserve the original result, explain any correction, and execute obligations an early failure skipped. On repeated failure, change the diagnosis or boundary rather than repeat an uninformative check.
8. `deliver` with real evidence, independently review and `accept` the observed result. When bytes or dependencies change, inspect stale state and `invalidate` the affected responsibility before renewed work. Keep old evidence immutable; use a new evidence file for a new observation. Record behavior and limitations, not just exit codes.
9. For another session, read `status`, chosen module `context`, real artifacts and latest evidence. Continue the next useful authorized action. Capture setup, build, assembly, review, correction and human effort when evaluating the method; avoid universal speedup claims from one successful project.

The core CLI stays project agnostic because module contracts and native artifacts are data. The host agent supplies judgment, the harness supplies agents, and the project remains the durable source of context. No global installation or custom model backend is required.
