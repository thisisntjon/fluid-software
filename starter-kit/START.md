# Start one useful outcome

**Method v0.2; working software foundation 0.1.0.** This portable method constructs an agent-usable project frame and builds within it. The executable entry point is described in [BUILD](BUILD.md) and the repository README. A real assisted software build and ordinary-workflow comparison are complete; cross-domain effectiveness and a general productivity multiplier remain unproven.

Use the project's existing plan, issues, contracts and evidence locations. The other files here describe fields that can be inserted into those records; copying every template is unnecessary. For a tiny change, one existing note containing the outcome, result and next action is enough.

For a substantial new or opaque project, begin with [Construct the project frame](SCAFFOLD.md). Make the complete intended whole visible, materialize the first usable foundations and boundaries, then dispatch ready parts. For an already navigable project, inspect and extend its frame rather than regenerate it.

## Rules when adopted

- Existing owner instructions, permissions, budgets and required CI remain authoritative. Reuse granted authorization; request a decision only when one is genuinely missing.
- Inspect relevant existing artifacts before rebuilding. Record consequential source versions and distinguish observations, interpretations and unknowns.
- Give each active output and shared mutable resource a clear owner. Workers stay within agreed boundaries.
- Change a shared contract explicitly; identify affected consumers and stale results.
- Support completion with the actual artifact and relevant real evidence. Do not fabricate inputs, test results or acceptance. Preserve existing required checks; report evidence gaps.
- Preserve accepted progress and enough state for a fresh worker to continue.

## Working sequence

1. **Name one useful outcome.** State who will use it and what observable change will satisfy them. Record constraints in [PROJECT](PROJECT.md).
2. **Inspect reuse.** Read an existing implementation, reference, source collection or prior attempt. Choose reuse, adapt, reference-only or new construction; explain material mismatch.
3. **Define boundaries.** Map responsibilities to the whole. Separately identify dependencies and shared decisions. Write [WORK-UNIT](WORK-UNIT.md) fields only for work needing delegation or continuity. If intended behavior or the approach is unresolved, use its exploration branch before assigning dependent builds.
4. **Build ready parts.** Parallelize only units with available inputs, stable-enough boundaries and independent ownership. Build coherent standalone outputs first.
5. **Assemble when ready.** Connect delivered parts whose dependencies are available. Exercise the actual consumer flow; return localized failures to an owner.
6. **Record the result.** Use [RESULT](RESULT.md). Distinguish a local check, assembled behavior and consumer acceptance. Stop optional checks when they cannot change a decision.
7. **Resume cold.** Read the current entry, relevant unit, output version and latest evidence. Confirm ownership and dependencies; do not assume old agents or sessions remain alive.

## Adjustable heuristics

Stop splitting when one worker can explain the responsibility, access its inputs, build within a bounded session, and demonstrate useful behavior without inventing another worker's decisions. Coarsen tightly coupled units. Limit parallel work when assembly or review queues grow. After repeated failure without new information, change the diagnosis, regroup or reassign. These are starting heuristics, not measured universal thresholds.

No delivery date or speedup is implied. Use actual constraints and observed effort.
